### ラリーの記録

#### C-1: DBマイグレーションの即時リネームリスク

- **R1 Codex**: ALTER TABLE RENAME を直接実行すると旧アプリが壊れる。2段階マイグレーション推奨。
- **R1 Claude**: 個人プロジェクトでCloudflare Pages（アトミックデプロイ）を使用。旧アプリが並行稼働する状況はない。過剰対策では？
- **R2 Codex**: **修正** — 個人プロジェクト＋アトミックデプロイなら即時リネームで問題ない。運用ノートとして記録を推奨。
- **結論**: 却下（アーキテクチャ上不要）

#### C-2: URL互換性（slots_desc → seats_desc）

- **R1 Codex**: 既存ブックマークが壊れる。リダイレクト or エイリアス推奨。
- **R1 Claude**: プレローンチ段階で外部ユーザーなし。既存ブックマークは存在しない。
- **R2 Codex**: **撤回** — プレローンチなら互換性対応は不要。
- **結論**: 却下（プレローンチのため不要）

#### A-2: NO_PLAYER_SLOTS_LEFT 定数名

- **R1 Claude**: grepでの網羅検索を妨げる旧用語残存。リネームすべき。
- **R2 Codex**: 内部定数名は外部影響なし。ただしリファクタリングの一貫性としてリネームはOK。
- **結論**: 採用（一貫性のためリネーム）

## 所見

今回のリネームは50ファイル・2000行超の大規模リファクタリングだったが、コード上の用語統一は概ね良好だった。
ただし、**日本語UI文言**において旧用語「提出枠」「確定枠」「可用枠」「日程枠」が15箇所以上残存していた。

Codex の指摘はインフラ寄り（DBマイグレーション戦略、URL互換性）で、このプロジェクトの規模・ステージには過剰だった。
一方、Claude のドメイン知識を活かした用語一貫性チェックが多くの改善を発見できた。

**教訓**: 大規模リネーム時は、コード上の識別子だけでなく、ログメッセージ・UI文言・テスト名も
grep で網羅的にチェックすべき。特に日本語文言は変数名と異なり型チェックで検出できないため、
手動検索が必須。
